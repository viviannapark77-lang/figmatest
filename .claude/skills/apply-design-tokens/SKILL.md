# /apply-design-tokens

**이 작업을 인라인으로 하지 않는다.** 반드시 `Agent`(subagent_type: `design-system-manager`)를 호출한다.

## 절차

### 1. 입력 확인 (호출 전)

| 필요 | 없으면 |
|---|---|
| 스타일을 입힐 UI 구조(트리) — `/analyze-prd` 또는 Layout Architect류 산출물 | 사용자에게 묻는다. 추측하지 않는다 |
| 대상 화면/기능명 (`{FeatureName}` — 산출물 파일명에 쓴다) | 사용자에게 묻는다 |
| 참조할 디자인 토큰 파일 경로 | 기본값으로 이 저장소를 쓰는 프로젝트라면 `src/tokens/**`. 다른 프로젝트/외부 디자인 시스템이면 경로를 사용자에게 확인한다 |

### 2. 에이전트 호출

`Agent`를 `subagent_type: "design-system-manager"`로 호출한다. 프롬프트에 반드시 포함:

- 스타일을 입힐 UI 구조(트리) 전체
- 디자인 토큰 파일 경로
- "레이아웃 구조·배치 순서는 건드리지 말고, styles 속성만 결합해 반환하라"
- "대응하는 토큰이 없는 값은 임의로 만들지 말고 목록으로 보고하라"

### 3. 반환 검증 + 파일 저장

`design-system-manager`는 `Write` 권한이 없어 파일을 직접 쓰지 않는다. 반환된 JSON/YAML을
확인한 뒤, **메인 세션이** `/docs/ui_specs/{FeatureName}-Styled_Structure.json`으로 저장한다.

확인 항목:
- 하드코딩된 px/Hex 값이 결과에 남아 있지 않다 (전부 토큰 이름으로 치환됨)
- 입력받은 구조의 계층·순서가 그대로 유지됐다
- Hover·Disabled·Error·Success 등 상태값이 필요한 곳에 할당돼 있다
- 속성 부여 이유에 대한 장황한 설명이 섞여 있지 않다

다음이면 다시 요청한다:
- 대응 토큰이 없다고 보고된 값이 있다 — 토큰을 먼저 추가할지 사용자에게 확인한다
- 구조가 원본과 달라졌다 (계층·순서 변경)
- 하드코딩된 값이 그대로 남아 있다

### 4. 다음 단계

이 산출물은 Figma 노드 생성 단계의 입력이다. 이 스킬은 Figma 노드를 직접 만들지 않는다 —
그 작업은 별도 스킬/에이전트의 역할이다.
